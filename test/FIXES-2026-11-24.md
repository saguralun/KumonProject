ขอบเขตรอบนี้: ใบเสร็จ, การส่งรับ DO ซ้ำ, reset รหัสผ่าน, WS และการกู้ AT/KSIS
ตามรายการที่พิสูจน์ใน [รีวิวเดิม](reviews/2026-11-24/README.md)
ทำต่อจาก working tree cleanup เดิม ไม่ย้อนหรือล้างงานที่มีอยู่

## พฤติกรรมที่เปลี่ยน

### ใบเสร็จ

- คงการพิมพ์ก่อนรับเงินและพิมพ์เบื้องหลัง เมื่อส่งพิมพ์ใบที่ยังไม่รับเงินแล้ว
  ล็อกวิชาและวิธีจ่ายให้ตรงกับกระดาษ แต่ยังรับเงินต่อได้ระหว่างงานพิมพ์รอผล
- ปุ่ม “แก้รายการหลังพิมพ์” ต้องยืนยันยกเลิกใช้กระดาษเดิม ตรวจ Preview ใหม่
  และพิมพ์ใหม่ก่อนรับเงิน ถ้าปิดใบที่พิมพ์แต่ยังไม่รับเงินจะแจ้งเรื่องกระดาษเดิม
- ใบเสร็จเดิมที่รับเงินแล้วและการออกบิลเพิ่มสำหรับวิชาที่ยังค้างยังแยกกันเหมือนเดิม
- ก่อนเขียนบิล เปรียบเทียบเลขใบเสร็จ นักเรียน งวด วิธีจ่าย วิชาและยอดกับ Preview
  ภายใต้ ledger lock ถ้าอีกเครื่องใช้เลขไปแล้วหรือข้อมูลเปลี่ยน ตอบ 409 ก่อนเขียน
  API รุ่นเก่าที่ไม่ส่ง snapshot ยังใช้ได้ ไม่แก้บิลหรือยอดเก่าของศูนย์
- แสดงเลข Billing หลังรับเงินต่อให้มีการ refresh และแยกผล “รับเงินแล้ว แต่โหลด
  รายการไม่สำเร็จ” จากการรับเงินล้มเหลว

### รับ DO

- UI เก็บรหัสคำขอเดิมพร้อมข้อมูลเมื่อคำตอบขาดหาย โหลดหน้าใหม่แล้วส่งซ้ำได้
  server คืนผลเดิม จำนวน 10 ไม่เพิ่มเป็น 20 จาก retry ของคำขอเดียว
- สำเร็จแล้วล้างรหัสคำขอฝั่ง UI การเพิ่มรอบใหม่ด้วยจำนวนเท่าเดิมยังทำได้
- ผูกคำขอกับผู้ใช้และข้อมูลที่ส่ง; ถ้าเปลี่ยนข้อมูลด้วยรหัสเดิมจะไม่เขียน
- ใช้ไฟล์บันทึกคำขอใน `backups/stock-receive-retries` หรือ directory ที่ตั้งค่าไว้
  ไม่เพิ่มตาราง/คอลัมน์ เก็บไฟล์ชุดนี้คู่กับฐานข้อมูล ไม่หมุนทิ้งแบบ logs
- ฐานข้อมูลกับไฟล์ไม่สามารถ commit เป็นธุรกรรมเดียวกันได้ หากหยุดกลางช่วง
  ที่ยังพิสูจน์ผลไม่ได้ จะบล็อกการทำซ้ำและให้ตรวจ DO ก่อนเริ่มรอบใหม่
  ไม่รับรองการย้าย/restore ที่นำไฟล์บันทึกกับฐานข้อมูลคนละชุดมารวมกัน
  รายละเอียดและเงื่อนไขการเก็บไฟล์อยู่ใน [DO retry protection](stockReceiveRetry.md)

### Reset รหัสผ่าน

- เปลี่ยนรหัสและลบ session เดิมของบัญชีเป้าหมายในธุรกรรมเดียวกัน
  การลบล้มเหลวต้อง rollback ไม่แจ้ง reset สำเร็จทั้งที่ยังไม่ได้ถอน session
- session เก็บ credential marker ฝั่ง server และตรวจเทียบค่าปัจจุบันทุกหน้า/API
  ที่ต้องใช้บัญชี จึงปฏิเสธ session เก่าที่คำขอค้างนำกลับมาบันทึกหลัง reset
- บัญชีอื่นและ Guest คงพฤติกรรมเดิม session รุ่นเก่าอัปเกรดได้ตราบเท่าที่
  row เดิมยังอยู่ ไม่บังคับทุกคน logout เพียงเพราะติดตั้งตัวแก้นี้
- Reset บัญชีตัวเองต้อง login ใหม่ด้วย งานที่ผ่านการตรวจสิทธิ์ไปก่อน reset
  อาจจบได้ แต่การเรียกครั้งต่อไปด้วย session เก่าจะไม่ผ่าน
- CLI สร้าง Admin ก่อนมี session table ยังทำได้ ตรวจว่า table ไม่มีจริงก่อน
  ข้ามการถอน session และไม่กลืน permission error หรือ SQL error อื่น

### WS

- Tab ตามด้วย Enter/Space เลือกผลค้นหาได้ คลิกเมาส์ไม่โหลดนักเรียนซ้ำ
- แก้วันที่สำเร็จจะอัปเดตแถวจากผลบันทึกก่อนอ่านประวัติ ถ้าอ่านไม่สำเร็จ
  เปิดช่องให้ใช้งานต่อและแจ้งสองผลแยกกัน ไม่คืนวันที่เป็นค่าเก่าทั้งที่บันทึกแล้ว
- ระหว่างแก้ประวัติ ล็อกการแก้ซ้อนของนักเรียนเดียวกัน และไม่เขียนผลทับนักเรียน
  ที่ผู้ใช้เพิ่งสลับไปเลือก
- เปลี่ยนเป็น 20/วันเมื่อไม่ได้เลือก Zun จะว่างทั้งสองช่อง หากเลือก Zun
  ต้องครบคู่ก่อนเปิด Save ไม่สร้างครึ่งชุดเอง ไม่เปลี่ยนลำดับ/วันที่ประวัติเดิม

### กู้ AT/KSIS เมื่อหลุด login

- รับทราบงานค้างได้จากหน้า login เดิมในแอปด้วย ไม่บังคับกลับ AT ก่อน login
- อธิบายและขอให้ผู้ใช้ยืนยันก่อนโหลดหน้า login ใหม่ ช่อง login ที่พิมพ์ค้าง
  จะถูกล้าง แต่ไม่สั่งรับเงินหรือบันทึก AT/WS ให้เอง
- โหลดหน้าเดิมขณะที่ write guard ยังอยู่ เพื่อล้าง timer เก่าก่อนปลด guard
  ไม่เดา URL login และไม่เพิ่มข้อยกเว้น POST แบบกว้าง
- หากมีข้อมูลแก้ค้าง คำขอบันทึกรอผล URL เปลี่ยน หรือโหลดไม่สำเร็จ ยังคง guard
  และ pending state; เมื่อกู้สำเร็จยังระบุว่าผลรอบก่อน **ไม่ยืนยัน** ต้องเตรียม
  AT ใหม่เพื่อตรวจผลเดิม ไม่ใช้ Preview เก่ากรอกซ้ำ

## ข้อมูลและอุปกรณ์

- ไม่เพิ่ม/ลบ/แก้ตารางหรือคอลัมน์ ไม่รัน migration กับฐานข้อมูลใช้งาน
- ไม่เปลี่ยนข้อมูลนักเรียน WS บิล ยอดรับเงิน และจำนวนคลังเดิม
- ไม่มีรายการจริง ไม่มีการพิมพ์จริง และไม่กรอก/บันทึก KSIS จริง
- ไม่ restart โปรแกรมใช้งาน ไม่ commit/push ระหว่างงานแก้และทดสอบนี้
- ใช้ PC 99% และ tablet 1% ตามเจ้าของระบบระบุ ไม่ออกแบบสำหรับ smartphone
  และตัดประเด็น layout จอ 390px ออกจากขอบเขตรอบนี้
- ข้อวิจารณ์เรื่องนโยบาย/UX อื่นใน 10 persona เป็นรายการพิจารณา ไม่อ้างว่า
  เปลี่ยนทุกข้อแล้ว เช่น default AT ผ่าน, Half Month, สิทธิ์ยกเลิกบิล และ draft Students

## หลักฐานทดสอบ

ใช้ browser/Electron fixtures ข้อมูลจำลอง และ PostgreSQL cluster ชั่วคราว
ที่ตรวจ owner/port/data directory ก่อนเปลี่ยนเส้นทางบริการทั้ง query/connect
ไม่ใช้ connection ของฐานข้อมูลใช้งานจริง

ผลรอบที่จบแล้ว:

- ชุดบริการ/สิทธิ์ทั้งโปรเจกต์: 325 ผ่าน, 4 ข้าม (โหมดทดสอบเฉพาะทางที่ไม่ได้เปิด)
- CLI สร้าง Admin: 3 ผ่าน
- Payment UI เว็บ/แอป: 28 ผ่าน รวม 6 กรณีใหม่ของการพิมพ์/ล็อก/แก้/ปิดใบ
- WS กรณีใหม่: 8 ผ่านทั้งเว็บและแอป โดย worker ตรวจ regression ที่เกี่ยวข้องรวม 26 ผ่าน
- PostgreSQL ชั่วคราวรอบสุดท้าย: 41 ผ่าน รวม parent test และ 40 subtests
  ครอบคลุม reset ข้ามเครื่อง, DO WS/CD ซ้ำ/เพิ่มใหม่/Process, เลขและยอดใบเสร็จ
  เปลี่ยนก่อนรับเงิน, ยกเลิกบิลเดิม, WS, สถานะ, FRGH และ restore ที่ล้มเหลว
- Syntax checks และ `git diff --check` ผ่าน
- UI ส่วนที่เหลือทั้งโปรเจกต์: 179 ผ่าน ไม่มีล้มเหลวหรือข้าม รวมกับ Payment
  และ WS กรณีใหม่เป็น 215 UI tests บนเว็บ/แอปด้วยข้อมูลจำลอง

รวม 584 รายการผ่าน (นับ parent/subtests ตาม Node test runner) และ 4 รายการ
restart helper เฉพาะทางที่ไม่ได้เปิด ไม่มีความล้มเหลวค้างจากรอบสุดท้าย
ไม่ได้อ้างว่าทดสอบทุกปุ่มครบทุกค่าของข้อมูลหรือยืนยันบริการ KSIS จริงแล้ว
สรุปผลและ fingerprint ของโค้ดอยู่ใน [fix-verification.json](reviews/2026-11-24/fix-verification.json)

ก่อนรอบสุดท้ายมีความผิดพลาดใน fixture ฐานทดสอบ: สร้าง session table ซ้ำกับ
schema เดิม และตั้ง username จำลองเกิน varchar(50) แก้เฉพาะ fixture แล้ว
รันฐานทดสอบทั้งชุดใหม่จนผ่าน ไม่แก้ schema เพื่อให้ test ผ่าน

ข้อจำกัดของ KSIS คือยังไม่ได้
ทดสอบการหมดอายุและ login กับบริการจริง ผลชุดกู้ AT เป็นการตรวจ service/guard
กับ UI จำลอง ซึ่งยังต้องสังเกตในการใช้งาน KSIS จริงรอบถัดไป
