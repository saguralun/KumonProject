# แก้ต่อจากรายงาน agent: WS/CD → คืน CD → Students → คลัง

รอบนี้ใช้ working tree เดิมต่อโดยไม่ล้างงานก่อนหน้า ไม่เปลี่ยน schema/master data
ไม่ทำรายการจริง ไม่พิมพ์จริง และไม่ใช้บัญชีหรือบันทึก KSIS จริง
ไม่มีการนำ mock UI มาเปลี่ยนหน้าจอใช้งาน รวมถึงไม่ได้เอาปุ่มลูกศร WS ออกจริง

## จำลองก่อนแก้

| ประเด็น | หลักฐานที่ทำให้ test ล้มเหลวก่อนแก้ | พฤติกรรมหลังแก้ |
| --- | --- | --- |
| WS สองชุดข้ามช่วง CD | เว็บ/แอป TRP 7A ชุด 41/51 มี CD 1 แล้ว แต่ Save ยังเปิด | อ่าน Main ทุกช่อง รวม CD ไม่ซ้ำ ให้ยืนยันรับ/ไม่รับทีละแผ่น เปิด Save เมื่อครบ และบอก CD ที่ยังเหลือ |
| ข้อความคืน CD ผิดบริบท | คืน CD ของ A แล้วเปิด B; ผลสำเร็จและ error ของ A ทับข้อความ B | ตรวจทั้งนักเรียนและรอบการโหลด profile ก่อน refresh/แจ้งผล ไม่เปลี่ยน ID ของคำขอหรือสูตรคืนคลัง |
| แก้วันเกิดเป็นอนาคต | UI ส่ง PUT และ service ยอม UPDATE วันเกิดในอนาคต | กันวันที่ที่เปลี่ยนเป็นอนาคตทั้ง UI/service ก่อนเขียน เก็บค่าที่พิมพ์ให้แก้ต่อได้ |
| ขอบเขตการลบวิชา | กล่องยืนยันมีเพียงวิชา/Enrollment ไม่บอกเด็กหรือ DT | ระบุชื่อเด็ก Student/Enrollment วิชา และแจ้งลบผล DT ก่อนยืนยัน สิทธิ์และข้อจำกัดการลบเดิมยังอยู่ |
| วันที่ตอนเพิ่ม DO เดิม | เปลี่ยน Out/Receive Date แล้วยังเพิ่มจำนวนได้โดยวันที่เดิมไม่เปลี่ยน | เทียบวันที่กับหัว DO ภายใต้ lock เดิม ถ้าต่างตอบ 409 และ rollback ก่อนเพิ่มจำนวน วันที่เดิมยังเพิ่มรายการตามปกติ |
| ผลค้นหา DO กลับสลับลำดับ | ค้น old → new แต่ผล old มาทีหลังและทับ FRESH | รับผลเฉพาะหมายเลขคำขอและตัวกรองปัจจุบัน ครอบคลุม error ของคำขอเก่าด้วย |
| จำนวนที่ยืนยันตัดคลัง | usage 4 รายการ/ของจริง 3 แต่ข้อความบอก 4 แผ่น/ชุด | แยกจำนวนบันทึกและ cutQuantity จริง รวมกรณี 0; API เก่าไม่ส่ง cutQuantity แสดงว่าไม่ทราบ ไม่เดาจาก usage |

หลักฐานก่อนแก้อยู่ใน `logs/round3-cd-before.log`, `round3-cd-return-before.log`,
`round3-student-service-before.log`, `round3-student-ui-before.log`,
`round3-stock-header-before.log` และ `round3-stock-ui-before.log`
กรณีวันเกิด fixture แรกขาด prefixId จึงแก้ fixture ให้ครบและตรวจข้อความ error
โดยเฉพาะก่อนเก็บหลักฐาน Missing expected rejection จริง ไม่ใช้ validation ช่องอื่น
เป็นหลักฐานของการตรวจวันเกิด

## ขอบเขตที่คงเดิม

- ไม่มีการรับ CD ให้อัตโนมัติ การไม่รับยังต้องยืนยัน และไม่บวก/ตัดคลังให้เอง
- CD ยังใช้ master ของศูนย์นั้น ไม่เพิ่ม master และคงพฤติกรรมเดิมเมื่อไม่มี CD master
  ที่ตรงกัน ไม่เปลี่ยน endpoint หรือรูปแบบคำขอ receive/save เดิม
- ทดสอบช่วง TRP 7A/6A ที่ 41/51, 91/101, 141/151 พร้อมคู่ซ้ำ/สลับลำดับ
  และรูปแบบช่องเดียว, 2 วัน, EFL, ME, รับ/ไม่รับ/ยกเลิก/ผิดพลาด/ลองใหม่/สลับเด็ก
- วันเกิดที่เป็นอนาคตอยู่ในข้อมูลเก่าแต่ไม่ได้เปลี่ยน ยังแก้ช่องอื่นได้ ไม่ปรับข้อมูลเก่า
  ให้อัตโนมัติ และไม่เพิ่มเกณฑ์อายุขั้นต่ำใหม่ให้การแก้ไข
- วันที่ DO ต่างกันจะหยุดอย่างชัดเจน ไม่ได้เพิ่ม API แก้วันที่ย้อนหลังในรอบนี้
  DO ที่ Process แล้ว การส่งซ้ำ การเพิ่มรอบใหม่ และการแก้จำนวนยังใช้ข้อจำกัดเดิม
  ผู้เรียกเก่าที่ไม่ส่ง Receive Date ยังเพิ่มรายการได้โดยไม่เปลี่ยนวันที่/งวดของ DO
  เดิม มีกรณีจำลองที่พบว่าตัวกันวันที่ครั้งแรกเข้มเกินไป แล้วแก้พร้อมตรวจซ้ำ
- สูตรตัดคลังไม่เปลี่ยน รายการไม่รับของจริงยัง Process ได้เพื่อเคลียร์รายการค้าง
- ไม่เปลี่ยนสูตรบิล สิทธิ์ Instructor สถานะเด็ก Half Month FRGH ลำดับประวัติ
  หรือกฎเลื่อนระดับ AT/Zun ใช้งานหลัก PC 99%/tablet 1%

## ผลทดสอบ

- ชุดบริการ/สิทธิ์ทั้งหมด: **338 ผ่าน**, ข้าม Windows restart helper เฉพาะทาง 1
  ไม่มีความล้มเหลวค้าง (`logs/round3-services-final.log`)
- PostgreSQL ชั่วคราวที่ตรวจ owner/port/data directory ก่อนใช้: **43 ผ่าน**
  รวม parent/subtests; มีกรณีวันเกิดและวันที่ DO เพิ่มจากชุดเดิม
- UI ที่เกี่ยวข้อง 25 ไฟล์: **131 กรณีไม่ซ้ำ** รอบกว้างผ่าน 129 และพบ
  สองกรณีตรวจเร็วเกินเหตุการณ์จริง: จบ Level ยังไม่เริ่ม/จบครบก่อนอ่านค่า
  และปุ่ม tablet ยังย้ายออกจาก panel ที่ซ่อนไม่เสร็จก่อนวัดตำแหน่ง
  ปรับ test ให้รอผล POST ของรอบนั้นและ DOM reflow ตามจริง ไม่เปลี่ยน logic AT
  หรือผ่อน assertions แล้วรันสองไฟล์ WS ทั้งชุด **18 ผ่าน** รวมสองกรณีเดิม
  จึงไม่มีกรณีล้มเหลวค้าง ไม่ได้นับการรันซ้ำเป็นกรณีใหม่
- หลังปรับ compatibility วันที่ DO ตรวจส่วนบริการคลังซ้ำ **13 ผ่าน** ไม่บวก
  ทับยอดชุดบริการเดิม และรัน PostgreSQL 43 กรณีใหม่พร้อมกรณี legacy นี้ผ่าน
- รวม **512 รายการทดสอบผ่าน**, ข้าม 1 Windows restart helper เฉพาะทาง
- ตรวจ syntax ของ application 6 ไฟล์และ `git diff --check` ผ่าน

รอบบริการครั้งแรกในสภาพจำกัดการเชื่อมต่อพบ fetch/EPERM ของเว็บทดสอบและ
การสร้าง junction จึงตรวจไฟล์สิทธิ์ซ้ำเพื่อแยกสาเหตุ แล้วรันชุดบริการทั้งหมดใหม่
ในสภาพที่เปิดเว็บทดสอบภายในเครื่องได้จนผ่าน ไม่แก้ application/assertions
เพื่อกลบผลทดสอบ ส่วน UI ใช้ startup allowance เดิม scale 3 เฉพาะ deadline
ของ test ไม่เปลี่ยน Playwright action timeout หรือเงื่อนไขตรวจ

ยังไม่ได้ commit/push/restart แอปจริง การหมดอายุของ KSIS กับบริการจริง
และรายการ agent อื่นนอกสี่ลำดับนี้ยังไม่อ้างว่าแก้ครบ
