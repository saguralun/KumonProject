**รายงานบทบาท 02 — ครูกรอก WS ปริมาณมากด้วยคีย์บอร์ด**

ตรวจจาก working tree ปัจจุบัน รวม cleanup ที่ยังไม่ commit และไฟล์ใหม่ที่เกี่ยวข้อง เช่น `dateHelpers.js` และหลักฐาน test ใหม่ ไม่ได้แก้ไฟล์ เปิดเบราว์เซอร์ คลิกจริง รันทดสอบ หรือเชื่อมระบบจริง รายงานนี้ไม่ครอบคลุมสอบ AT และไม่พบหลักฐานเพียงพอให้จัดเป็น P1

**1) บุคลิกและงานเป้าหมาย**

ครูที่กรอก WS ต่อเนื่องหลายสิบคนจากกองใบงาน ใช้ชื่อไทย ชื่อเล่น หรือ ID เพื่อเลือกเด็ก สลับวิชา เลือกวันที่และ pattern แล้วกด Enter ต่อเนื่อง ต้องแก้รายการผิดได้เร็ว และแยกออกว่าข้อมูลใด “บันทึกล่าสุด” กับ “วันที่ WS ล่าสุด”

เกณฑ์สำคัญคือจำนวนจังหวะคีย์ ความสม่ำเสมอของค่าเริ่มต้น ความตรงกันระหว่าง Preview กับ Save และความมั่นใจเมื่อแก้ประวัติ

**2) เส้นทางใช้งานและปุ่มสำคัญที่ตรวจ**

ทั้งหมดเป็นการจำลองจาก UI → handler → service:

- **ค้นหา:** ช่องเดียวรองรับ ID/ชื่อ/ชื่อเล่น กรอง ALL/ME/EFL/TRP ใช้ ↑/↓ และ Enter เลือกผลลัพธ์ การค้นหา ID จัด exact match ก่อน ส่วนชื่อและชื่อเล่นค้นหาแบบมีข้อความนั้นอยู่ภายใน ([service:486](D:/Project/KumonDB/services/worksheetService.js:486))
- **เลือกเด็กและวิชา:** โหลดระดับ Main/Zun ประวัติ และค่าเริ่มต้นใหม่ แล้วส่งโฟกัสไป Main ช่องแรก การเปลี่ยน Subject เรียกโหลด context ใหม่ ([worksheet.js:68](D:/Project/KumonDB/public/js/worksheet/worksheet.js:68), [worksheet.js:514](D:/Project/KumonDB/public/js/worksheet/worksheet.js:514))
- **Receive Date:** เริ่มจากวันที่ WS สูงสุดบวกหนึ่งวัน ใช้ปุ่ม ◀/▶ หรือ ←/→ เลื่อนวัน และ Enter เข้าช่อง Main ([service:753](D:/Project/KumonDB/services/worksheetService.js:753), [keyboard:51](D:/Project/KumonDB/public/js/worksheet/worksheetKeyboard.js:51))
- **WS/day และ Main/Zun:** ตรวจ 20/วัน, 10/วัน และกระจาย 2–5 วัน; ↑/↓ เปลี่ยนเลข, `0` ล้าง Zun, Enter ไปช่องถัดไป และ Enter ช่องสุดท้ายเรียก Save โดยตรง ([worksheet.js:191](D:/Project/KumonDB/public/js/worksheet/worksheet.js:191))
- **Preview/Save:** Preview เปลี่ยนตามช่องกรอก บันทึกแล้วเพิ่มประวัติ ขยับ Receive Date และกลับ Main ช่องแรก ส่วนปุ่ม Main/Zun บนวงความคืบหน้าเปลี่ยนกราฟที่ดู ไม่ได้เลือกว่าจะบันทึกกลุ่มใด
- **แก้ประวัติ/ลบ:** เลขและวันที่บันทึกด้วย Enter; Esc หรือออกจากช่องยกเลิกค่า ลบทีละ record พร้อมยืนยัน และ service ปฏิเสธการแก้/ลบแถวที่ตัด stock แล้ว
- **หา WS ค้าง:** แยกเด็กปกติกับ KC โดยหา Main WS ล่าสุดก่อนวันที่ 21 ของเดือนปัจจุบัน ไม่ได้อิง Receive Date ที่กำลังกรอก ([service:579](D:/Project/KumonDB/services/worksheetService.js:579))

**3) ข้อวิจารณ์ เรียงความรุนแรง**

**① P2 — เปลี่ยนเป็น 20/วันแล้วระบบสร้าง Zun ครึ่งชุดเอง แต่ Preview ยังบอกพร้อมบันทึก**

**สถานการณ์:** เลือกเด็กที่มีระดับ Zun แต่ไม่มีประวัติ Zun ระดับนั้นอยู่ใน context แล้วเปลี่ยนจาก 10/วันเป็น 20/วัน

**ยืนยันจากโค้ด:** ช่อง Zun แรกเริ่มว่าง แต่ช่องที่สองใช้ `nextDefaultNo()` จากค่าว่าง จึงเลือกเลขแรกใน options ให้เอง ([preview:298](D:/Project/KumonDB/public/js/worksheet/worksheetPreview.js:298), [input:67](D:/Project/KumonDB/public/js/worksheet/worksheetInput.js:67)) Preview ยอมแสดง Zun เพียงช่องเดียว และเงื่อนไขเปิด Save ตรวจความครบเฉพาะ Main ([input:113](D:/Project/KumonDB/public/js/worksheet/worksheetInput.js:113), [preview:538](D:/Project/KumonDB/public/js/worksheet/worksheetPreview.js:538)) แต่ service กำหนดว่าเมื่อ Zun มีค่าแม้ช่องเดียว ต้องตรวจทั้งสองช่อง จึงปฏิเสธชุดนี้ ([service:1461](D:/Project/KumonDB/services/worksheetService.js:1461))

**ผลกระทบ:** ครูตั้งใจกรอก Main อย่างเดียว แต่ถูกหยุดด้วยข้อผิดพลาดจากค่า Zun ที่ระบบใส่เอง ความหมายของ “Optional” และ Preview จึงไม่น่าเชื่อถือ ไม่ใช่หลักฐานว่าข้อมูลผิดถูกบันทึกแล้ว เพราะ service ป้องกันไว้

**แนวปรับเล็กและชัด:** เมื่อ Zun ช่องแรกว่าง ให้ช่องสองว่างด้วย และให้ Preview ตรวจเงื่อนไข “ว่างทั้งคู่หรือครบทั้งคู่” ก่อนเปิด Save

**② P2 — แก้วันที่สำเร็จ แต่โหลดประวัติพลาดแล้วช่องค้างปิดใช้งาน พร้อมข้อความสำเร็จที่กลบปัญหา**

**สถานการณ์:** กด Enter แก้วันที่ → PATCH สำเร็จ → คำขอโหลด history ต่อมาล้มเหลว

**ยืนยันจากโค้ด:** handler ปิดช่องก่อนส่งคำขอ แล้วรอ `refreshHistory()` โดยไม่ตรวจผลลัพธ์ ก่อนแสดง “แก้วันที่แล้ว” ([worksheet.js:350](D:/Project/KumonDB/public/js/worksheet/worksheet.js:350)) ขณะที่ `refreshHistory()` จับ error และคืน `false` เอง จึงไม่เข้า catch ของ handler แก้วันที่ ([worksheet.js:175](D:/Project/KumonDB/public/js/worksheet/worksheet.js:175)) ไม่มีการนำ `result.entry` มาอัปเดตแถวหรือเปิดช่องคืนในเส้นทางนี้ อีกทั้งการมีช่องวันที่ disabled ทำให้ handler แก้เลข WS ไม่ยอมเริ่มงานด้วย ([worksheet.js:382](D:/Project/KumonDB/public/js/worksheet/worksheet.js:382))

**ผลกระทบ:** วันที่ในฐานข้อมูลแก้แล้ว แต่ประวัติในหน้าจอยังเป็น state เก่า ครูอาจแก้เลขต่อไม่ได้จนกว่าจะโหลดประวัติสำเร็จ ทั้งที่ข้อความหน้าจอรายงานสำเร็จอย่างเดียว

**แนวปรับเล็กและชัด:** ใช้ `result.entry` อัปเดตแถวทันที ตรวจค่าที่คืนจาก `refreshHistory()` และเปิดช่องคืนใน `finally` พร้อมแจ้งแยกว่า “บันทึกแล้ว แต่โหลดประวัติไม่สำเร็จ” แบบที่เส้นทางแก้เลขทำอยู่แล้ว

**③ P2 — “หา WS ค้าง” เปิดได้ด้วยคีย์บอร์ด แต่เลือกเด็กในตารางไม่ได้ด้วยคีย์บอร์ดมาตรฐาน**

**สถานการณ์:** Tab ไปปุ่ม “หา WS ค้าง” แล้ว Enter จากนั้นพยายาม Tab เลือกเด็กในรายการ

**ยืนยันจากโค้ด:** รายการเด็กเป็น `<tr>` ที่ไม่มีปุ่ม ลิงก์ หรือ `tabindex` ([incomplete:43](D:/Project/KumonDB/public/js/worksheet/worksheetIncomplete.js:43)) การเลือกผูกเฉพาะ event `click` ของตาราง ([worksheet.js:641](D:/Project/KumonDB/public/js/worksheet/worksheet.js:641)) CSS แสดงเพียง cursor และ hover ของเมาส์ ([worksheet.css:1613](D:/Project/KumonDB/public/css/worksheet.css:1613))

**ผลกระทบ:** เส้นทางตามเก็บงานค้างบังคับให้ครูเปลี่ยนไปใช้เมาส์ แม้เส้นทางกรอกหลักรองรับ Enter ต่อเนื่อง

**แนวปรับเล็กและชัด:** ใส่ปุ่ม “เลือกเด็ก” ในแต่ละแถว ใช้ native Enter/Space และย้ายโฟกัสเข้ารายการเมื่อเปิดหน้าต่าง คืนโฟกัสไปปุ่มเดิมเมื่อปิด

**④ P2 — ผลค้นหาเป็นปุ่มที่ Tab ถึงได้ แต่ Enter บนปุ่มไม่เลือกเด็ก**

**สถานการณ์:** พิมพ์ชื่อ รอรายการขึ้น แล้ว Tab จากช่องค้นหาไปปุ่มผลลัพธ์และกด Enter

**ยืนยันจากโค้ด:** ผลลัพธ์สร้างเป็น `<button>` ([search:22](D:/Project/KumonDB/public/js/worksheet/worksheetSearch.js:22)) แต่ handler เลือกผูกกับ `mousedown` เท่านั้น ([worksheet.js:496](D:/Project/KumonDB/public/js/worksheet/worksheet.js:496)) ส่วน Enter ที่เลือกเด็กได้ผูกเฉพาะช่องค้นหา ([worksheet.js:486](D:/Project/KumonDB/public/js/worksheet/worksheet.js:486))

**ผลกระทบ:** ผู้ใช้ที่ใช้ ↑/↓ ในช่องค้นหาทำงานได้ แต่ผู้ใช้ที่เดินด้วย Tab พบปุ่มที่ดูใช้งานได้แต่ไม่ตอบสนอง การอ่านโค้ดรองรับข้อสรุปนี้; ยังต้องยืนยัน event จริงใน synthetic UI

**แนวปรับเล็กและชัด:** ให้ delegated `click` เป็นทางเลือกหลักที่รองรับเมาส์และคีย์บอร์ด และคง `mousedown` ไว้เฉพาะจัดการโฟกัสตามจำเป็น โดยป้องกันการเลือกซ้ำ

**⑤ P3 — pattern กลับเป็น 10/วันทุกครั้งที่เปลี่ยนเด็กหรือวิชา ทำให้จังหวะงานไม่ต่อเนื่อง**

**สถานการณ์:** กรอกกองงานแบบ 5 วันให้เด็กคนแรก แล้วเลือกคนถัดไปและกรอกต่อด้วยความเคยชิน

**ยืนยันจากโค้ด:** service ส่ง default pattern เป็น `daily10` เสมอ และการโหลด context เขียนทับ pattern ปัจจุบันทุกครั้ง ([service:200](D:/Project/KumonDB/services/worksheetService.js:200), [service:1406](D:/Project/KumonDB/services/worksheetService.js:1406), [worksheet.js:99](D:/Project/KumonDB/public/js/worksheet/worksheet.js:99))

**ข้อวิจารณ์ UX:** ไม่ใช่บั๊กตามข้อกำหนดที่พิสูจน์ได้ แต่เพิ่มการเลือกซ้ำทุกคน และเสี่ยงบันทึกเพียงวันเดียวหากครูคิดว่า pattern เดิมยังอยู่

**แนวปรับเล็กและชัด:** เพิ่มตัวเลือก “คง WS/day สำหรับคนถัดไป” ภายใน session โดยแสดงสถานะให้เห็นชัด ไม่ควรเปลี่ยนเป็นจำค่าเงียบ ๆ โดยไม่มีตัวบอก

**⑥ P3 — Tab ทิ้งการแก้ประวัติเงียบ ๆ ขัดกับงานแก้หลายแถว**

**สถานการณ์:** พิมพ์เลขหรือวันที่ใหม่ แล้ว Tab ไปช่องถัดไปเพื่อแก้ต่อ

**ยืนยันจากโค้ดและ test:** blur คืนค่าเดิมทั้งเลขและวันที่ ([worksheet.js:601](D:/Project/KumonDB/public/js/worksheet/worksheet.js:601)) และ test ระบุชัดว่า Tab หลังแก้เลขต้องกลับเป็นค่าเดิม ([number-edit test:53](D:/Project/KumonDB/test/worksheetNumberEdit.ui.test.js:53)) จึงเป็นพฤติกรรมที่ตั้งใจ ไม่ใช่ regression ที่กล่าวอ้างได้

**ข้อวิจารณ์ UX:** ผู้ใช้ตารางจำนวนมากคุ้นกับการพิมพ์แล้ว Tab ต่อ จึงอาจเข้าใจว่าแก้แล้วทั้งที่ค่าถูกยกเลิก โดยช่องวันที่ไม่มีคำแนะนำ Enter/Esc แบบที่ใส่ไว้ใน title ของช่องเลข ([history:103](D:/Project/KumonDB/public/js/worksheet/worksheetHistory.js:103), [history:125](D:/Project/KumonDB/public/js/worksheet/worksheetHistory.js:125))

**แนวปรับเล็กและชัด:** แสดงข้อความถาวรใกล้ตารางว่า “Enter บันทึก • Esc/ออกจากช่อง ยกเลิก” และแจ้งสั้น ๆ เมื่อยกเลิกค่าที่เปลี่ยนเพราะ Tab โดยยังคงกติกาบันทึกเดิมได้

**4) สิ่งที่ทำดี**

- **เส้นทางคีย์บอร์ดหลักมีฐานที่ดี:** ค้นหาช่องเดียว รองรับ Enter ทันทีแม้ยังอยู่ในช่วงรอค้นหา แล้วส่งโฟกัสเข้า Main มี test ครอบคลุมชื่อเล่นไทย ID และการกรองวิชา ([search test:19](D:/Project/KumonDB/test/worksheetUnifiedSearch.ui.test.js:19)) cleanup ยังทำให้ Preview กับ Save ใช้ตัวอ่านเลขชุดเดียวกัน ลดโอกาสแสดงกับส่งข้อมูลคนละค่า
- **แยกประวัติการกรอกกับวันที่ล่าสุดได้เหมาะกับงานแก้ย้อนหลัง:** History เรียง ID ใหม่ก่อน ขณะที่ความหมาย “WS ล่าสุด” ใช้วันที่แล้วค่อย ID มี test แยกสองกติกานี้ชัด ([history-order test:7](D:/Project/KumonDB/test/worksheetHistoryOrder.test.js:7)) จึงไม่ควรรายงานการเรียง History แบบนี้เป็นบั๊ก

**5) ข้อจำกัดและกรณีที่ควรทดสอบเพิ่มเติม**

อ่าน test เพื่อดูความตั้งใจและความครอบคลุมเท่านั้น **ไม่ได้ยืนยันว่า test ผ่านในรอบนี้** และไม่ได้ใช้ผลรันที่บันทึกไว้ในเอกสาร cleanup แทนการตรวจจริง

กรณีที่ควรให้ parent ตรวจใน synthetic UI ตามลำดับ:

1. เด็กมี Zun แต่ไม่มีประวัติ → เปลี่ยน 20/วัน → ตรวจค่าเริ่มต้น Preview และการปฏิเสธ Save
2. แก้วันที่สำเร็จแต่ history ตอบ 503 → ตรวจข้อความ ช่องวันที่ และการแก้เลขต่อ
3. ใช้คีย์บอร์ดล้วนเลือกผลค้นหาด้วย Tab/Enter และเลือกเด็กจาก “หา WS ค้าง”
4. กรอกหลายคนด้วย pattern เดิม แล้วสลับ Subject ตรวจจำนวนจังหวะคีย์และความชัดของ pattern ที่ถูกรีเซ็ต
5. ตรวจ Windows date input จริงเมื่อใช้ ←/→ พิมพ์ปี และ Enter รวมถึงโฟกัสหลังแก้ประวัติสำเร็จ และการแก้/ลบชุด 5 วันทั้ง Main–Zun โดยไม่หลงแถว

ประเด็นที่ยืนยันจากโค้ดข้างต้นเป็นพฤติกรรมของ working tree ปัจจุบัน ยังไม่มีหลักฐานว่าทั้งหมดเกิดจาก cleanup รอบนี้โดยตรง
