# รีวิวผู้ใช้จำลอง 10 บทบาท — 24 พฤศจิกายน 2026

**ยังรับรองว่า “ทุกปุ่มทำงานปกติครบทุกเงื่อนไข” ไม่ได้** ชุดทดสอบมาตรฐานทำงานตามเงื่อนไขที่เขียนไว้ แต่การจำลองสถานการณ์เพิ่มพบปัญหาที่เงื่อนไขเดิมไม่ครอบคลุม ทั้งด้านข้อมูลบนใบเสร็จ การกู้งานเมื่อเกิด error และการใช้งานด้วยคีย์บอร์ด/จอเล็ก

รอบนี้เป็นการตรวจและวิจารณ์ ไม่แก้กติกาธุรกิจ ไม่เปลี่ยน schema ไม่ทำรายการจริง ไม่พิมพ์จริง และไม่กรอก/บันทึก KSIS จริง ผลไม่ได้ยืนยันว่าปัญหาทั้งหมดเกิดจาก cleanup ก่อนหน้า

## วิธีตรวจและขอบเขตหลักฐาน

- ใช้ agent อิสระ 10 ตัว จำลองความต้องการและเส้นทางงานคนละบทบาทจาก working tree ปัจจุบัน แต่ละรายงานระบุชัดว่าเป็นการอ่านโค้ด ไม่ใช่คนจริงหรือการคลิกจริง
- เป็นการจำลองมุมมองและเส้นทางงาน ไม่ใช่การวัดโหลดผู้ใช้ 10 คนพร้อมกัน
- Parent รัน UI workflow tests ทุกไฟล์: **196 กรณี** รอบหลักผ่าน 192 ล้มเหลว 2 และยกเลิกเพราะหมดเวลา 2; ตรวจซ้ำแยกทั้ง 4 กรณีผ่านครบ ไม่ได้รันรวมใหม่ทั้ง 196 ในครั้งเดียว
- รอบหลักพบ `ERR_NETWORK_IO_SUSPENDED` และเวลาทดสอบกระโดดราวหนึ่งชั่วโมงในบางเคส จึงแยกผลสภาพแวดล้อมออกจากข้อบกพร่อง ไม่ตัดสินจาก timeout เพียงอย่างเดียว
- บันทึก click จาก UI จำลองได้ 1,010 events จับคู่กับปุ่มใน HTML ได้ **129 จาก 218 จุด**: 102 ด้วย ID และ 27 ด้วยข้อความที่ไม่ซ้ำในหน้านั้น อีก **89 จุดยังไม่มี click ที่จับคู่ตรงในบันทึกนี้** ไม่ได้แปลว่า 89 จุดเสียหรือไม่มี test เพราะบางเส้นทางตรวจด้วย hover/คีย์บอร์ด/สถานะ disabled และบางปุ่มเกิดภายหลัง
- ปุ่ม/ลิงก์ที่เกิดภายหลังบันทึกแยก 117 และ 7 signatures ตามลำดับ ไม่มีตัวหารครบทุกข้อมูลและทุกสถานะ จึงไม่ใช้เป็นเปอร์เซ็นต์ครอบคลุมทั้งโปรแกรม
- UI ใช้เว็บจำลองและ Electron profile ชั่วคราว การพิสูจน์ service ใช้ dependency/SQL mocks ที่ปิดทางเชื่อมข้อมูลจริง ผลแต่ละข้อแยกระดับหลักฐานไว้ด้านล่าง

ดู [ตารางรายหน้าและจุดที่ยังจับคู่ไม่ได้](control-coverage.md) และ [ข้อมูลตรวจฉบับเต็ม](control-coverage.json)

### ข้อสังเกตด้านการทดสอบ

กรณี AT สองหน้าต่างเคยรอปุ่ม Preview ที่ถูกซ่อนในรอบหลัก แล้วผ่านเมื่อรันเดี่ยว ยังไม่สรุปว่าเป็นบั๊กถาวรหรือหายแล้ว ควรเพิ่มการบังคับให้ผล shared workspace กลับสลับลำดับก่อนปิดประเด็นนี้

## ลำดับงานที่แนะนำ

1. ตัดสิน workflow เอกสารก่อนรับเงิน แล้วผูกสิ่งพิมพ์กับรายการที่รับจริง; กันคำขอ DO ซ้ำ; ถอน session เมื่อ reset password; ยืนยัน recovery AT ครบสายก่อนแก้ guard
2. แก้การกู้งาน WS เมื่อ refresh ล้มเหลว, Zun ไม่ครบ, keyboard selection และ layout จอเล็ก พร้อม regression tests ที่คาดว่าปัญหาเหล่านี้ต้องไม่เกิด
3. เก็บ draft ฟอร์มและป้องกัน stale edits; แสดงผลกระทบก่อนลบ/เปลี่ยนสถานะ; ปรับหน่วยตัวเลขและคำอธิบายข้อมูลไม่ครบ
4. ทบทวนนโยบายที่ต้องให้เจ้าของระบบเลือกก่อน เช่น พิมพ์ก่อนรับเงิน, default AT ผ่าน, Half Month เปลี่ยน Start Date และสิทธิ์ยกเลิกบิล อย่าเปลี่ยนพฤติกรรมเหล่านี้เงียบ ๆ ระหว่างจัดโค้ด

สคริปต์ audit เป็นหลักฐานพฤติกรรม ณ รุ่นที่รีวิว ไม่ใช่ regression tests ที่รับรองความถูกต้องทุกกรณี บางข้อยืนยันว่าปัญหายังเกิด เมื่อแก้โปรแกรมต้องปรับความคาดหวังและเพิ่ม test ของพฤติกรรมที่ถูกต้อง ดูวิธีรันใน [scripts/audits/README.md](../../../scripts/audits/README.md)
